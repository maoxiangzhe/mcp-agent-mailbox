# MCP 智能体邮箱只读监控台设计

状态：待实现  
日期：2026-10-04  
适用版本：`mcp-agent-mailbox 0.3.x`

## 1. 目标

为 MCP 智能体邮箱增加一个仅监听本机回环地址的 Web 监控台，让使用者能直接观察：

- 邮箱账号、宿主身份、连接和在线状态；
- 对话、参与者、未读数量和最新活动；
- 消息正文、回复关系以及彼此独立的投递、可见性、处理状态；
- 待投递、重试、失败与死信；
- 数据库、Broker 配置和宿主适配器能力诊断。

监控台是现有权威状态的只读投影，不是第二套邮箱客户端，也不是 MCP 或宿主适配器的替代品。

## 2. 非目标与硬边界

第一版不提供下列能力：

- 发送消息、回复消息；
- 标记已读、修改处理状态；
- 确认、失败、重试或删除投递；
- 注册账号、续租连接、唤醒宿主；
- 修改配置、执行迁移或修复数据库；
- 把未验证的 Level 2 能力显示成可用。

所有 HTTP API 均为只读。浏览器不得直接打开 SQLite，不得从日志或 Markdown 反向解析权威状态。

## 3. 技术方案

### 3.1 选型

采用 Python 标准库 HTTP 服务和仓库内置的原生 HTML、CSS、JavaScript：

- 不新增 Node.js 构建链；
- 不依赖 CDN、远程字体或第三方前端服务；
- 复用项目现有 SQLite 仓储、配置和领域对象；
- 静态资源随 Python 包分发；
- 可通过一个 CLI 子命令启动。

FastAPI 加 SPA 框架会增加运行依赖、打包和升级成本，第一版不采用。前端直接查询 SQLite 会破坏应用边界，也不采用。

### 3.2 模块边界

新增 `mcp_agent_mailbox/dashboard/`：

```text
dashboard/
├── __init__.py
├── server.py          # 回环 HTTP 服务、鉴权、路由、静态资源
├── queries.py         # 只读查询门面，组合现有仓储结果
├── serializers.py     # 领域对象到稳定 JSON DTO
└── static/
    ├── index.html
    ├── app.css
    └── app.js
```

`queries.py` 是 UI 与存储实现之间的边界。它可以使用现有 Unit of Work 和只读 SQL 查询，但不得提交业务状态变化。诊断查询若尚无公共仓储接口，应新增明确的只读查询方法，禁止把 SQL 写进浏览器或模板。

### 3.3 启动入口

CLI 增加：

```bash
uv run python -m mcp_agent_mailbox.cli dashboard
uv run python -m mcp_agent_mailbox.cli dashboard --host 127.0.0.1 --port 8765
```

约束：

- 默认且建议绑定 `127.0.0.1`；
- 非回环地址必须显式指定，启动时输出明显安全警告；
- 端口冲突应给出可操作错误，不静默换端口；
- 服务停止后释放数据库连接和 HTTP 线程。

## 4. 安全模型

消息正文属于敏感数据，即使服务只监听本机也必须鉴权。

启动时生成高熵临时令牌，并打印包含令牌的本地访问 URL。页面首次加载后仅将令牌保存在当前页面内存或 `sessionStorage`，API 请求使用：

```http
Authorization: Bearer <token>
```

安全要求：

- 不把令牌写入项目、数据库或日志文件；
- 不使用 `localStorage`；
- API 未授权统一返回 `401`，不泄露诊断或实体是否存在；
- 默认拒绝跨域读取，不设置宽泛的 CORS；
- 设置严格 CSP，禁止外部脚本、样式、字体和连接；
- 设置 `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`；
- 错误响应不返回堆栈、绝对路径、SQL 或消息正文；
- 页面所有正文以文本渲染，禁止把消息内容注入 `innerHTML`。

## 5. 只读 API

统一响应包含：

```json
{
  "ok": true,
  "data": {},
  "meta": {
    "generated_at": "ISO-8601",
    "next_cursor": null,
    "has_more": false
  }
}
```

建议端点：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/overview` | 总览计数、积压、死信、当前连接和能力分布 |
| `GET /api/accounts` | 分页列出账号、当前连接、在线状态和能力 |
| `GET /api/accounts/{id}` | 单账号详情和连接证据 |
| `GET /api/conversations` | 按账号、未读状态、活动时间分页筛选对话 |
| `GET /api/conversations/{id}` | 对话元数据与参与者 |
| `GET /api/conversations/{id}/messages` | 游标分页加载消息与三维状态 |
| `GET /api/deliveries` | 按状态、账号、对话筛选投递 |
| `GET /api/diagnostics` | 数据库、迁移、Broker 配置与能力验证状态 |
| `GET /api/health` | 不含敏感内容的服务存活信息 |

只允许 `GET` 和必要的 `HEAD/OPTIONS`。对 `/api/*` 发送 `POST`、`PUT`、`PATCH`、`DELETE` 必须返回 `405`。

所有列表必须有稳定排序、上限和游标，不能把整张表一次性送入浏览器。API 的 `total` 必须来自聚合查询，不能用当前页数量冒充全局总数。

## 6. 状态表达

页面必须把以下概念分开：

```text
delivery:   queued -> dispatched -> delivered | failed | dead_letter
visibility: unread -> seen
processing: pending -> running -> completed | blocked | cancelled | failed
```

回复是带 `reply_to` 的新消息，不等于处理完成；`delivered` 只代表宿主可靠接收，不等于模型已完成任务。

宿主能力至少展示：

- 声明能力等级 `level`；
- 当前是否连接 `connected`；
- 是否具备唤醒能力 `can_wake`；
- 是否经过真实验证 `verified`；
- 证据或降级原因。

`verified=false`、无跨进程事件通道、Level 0/1 均必须使用明确文字，不得仅依靠颜色，也不得显示“实时可达”等误导性文案。

## 7. 页面信息架构

### 7.1 全局框架

桌面端采用左侧导航、顶部系统状态带、右侧主工作区。移动端折叠为顶部导航和纵向卡片。页面包括：

1. 总览；
2. 账号；
3. 对话；
4. 投递；
5. 诊断。

视觉方向为“本地通信枢纽/运维控制台”：石墨深色背景、温暖的琥珀信号色、青绿色正常状态、红橙色故障状态。避免通用紫色渐变和模板化卡片墙。

### 7.2 总览

- 账号总数、当前在线数；
- 未读消息总数；
- queued、failed、dead-letter 数量；
- Level 0/1/2 分布与真实验证数量；
- 最近活动时间线，只显示事件类型、关联 ID 和时间，不显示正文。

### 7.3 账号

表格字段包括显示名、宿主类型、宿主实例、原生会话 ID、presence、能力等级、`can_wake`、`verified`、最后心跳。详情抽屉展示连接代次、租约和降级证据。

### 7.4 对话与消息

采用主从布局：左侧筛选和对话列表，右侧加载选中对话的参与者及消息。

- 列表展示参与者、未读数、最后活动和阻塞状态；
- 消息正文仅在选中对话后按页加载；
- 回复关系可以跳转到被回复消息；
- 消息卡片分别展示 delivery、visibility、processing；
- 页面读取不得改变已读位点或任何处理状态。

### 7.5 投递

按 `queued / dispatched / delivered / failed / dead_letter` 筛选，展示 delivery ID、消息 ID、目标账号、尝试次数、下一次重试、失败摘要和时间。失败原因默认折叠。

### 7.6 诊断

- 数据库路径只显示脱敏后的必要部分；
- SQLite 完整性、迁移版本、WAL 状态；
- Broker 是否仅为当前进程实例；
- 跨进程事件通道是否实现；
- 各宿主适配器的声明等级与验证状态；
- 当前生效的非敏感配置。

诊断页面不得把“接口存在”解释成“真实唤醒已验证”。

## 8. 交互、可访问性与性能

- 首次加载只请求 overview；进入区域后再加载明细；
- 筛选输入防抖，旧请求可忽略，避免结果乱序；
- 提供手动刷新以及 5/15/30 秒自动刷新，默认关闭；
- 自动刷新暂停时有明确状态；
- 所有可交互元素支持键盘和可见焦点；
- 状态同时使用文字、图标和颜色；
- 尊重 `prefers-reduced-motion`；
- 在 320、768、1024、1440 像素宽度下无横向溢出；
- 空状态、加载状态、鉴权失败、数据库忙、实体消失分别显示；
- API 超时或失败不得用旧数据伪装成当前成功，应标出最后成功刷新时间。

## 9. 测试策略

### 9.1 查询与 API

- 空数据库返回稳定结构；
- 账号、对话、消息、投递分页和筛选正确；
- 全局总数不受当前页上限影响；
- 消息查询不更新未读数或处理状态；
- 未授权请求返回 401；
- 所有写方法返回 405；
- 不存在资源返回 404，非法游标返回 400；
- 数据库忙或损坏返回脱敏的 503/500；
- CSP、安全头和静态资源类型正确。

### 9.2 页面

- 导航、筛选、分页、详情展开和刷新可用；
- 空、加载、错误、未验证、未连接状态均有明确展示；
- 消息正文按纯文本显示，恶意 HTML 不执行；
- 窄屏布局不溢出，键盘可操作，减少动画设置生效。

### 9.3 回归

完成后必须运行：

```bash
uv run python run_tests.py
```

新增控制台不得改变 MCP 工具注册、账号绑定、投递状态机和既有 CLI 行为。

## 10. 验收标准

1. 一条命令可在本机启动控制台并输出临时访问地址；
2. 用户能查看账号、连接、对话、消息、投递和诊断；
3. 页面没有任何业务写操作；
4. 浏览页面前后，数据库业务表内容完全一致；
5. 100 条以上数据仍通过分页稳定浏览，总数准确；
6. Level 2 未验证或跨进程事件未实现时，页面明确显示限制；
7. 未持有临时令牌无法读取任何敏感 API；
8. 完整测试与新增测试全部通过。
