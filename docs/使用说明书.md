# MCP 智能体邮箱 · 使用说明书

> 版本：对应本仓库当前代码（`main` 工作区，未打 tag）。
> 本文只写**能做到的**和**做不到的**，不写设想。凡是"实测通过/未实现"都单独标注。

## 一、这是什么

一个**会话寻址**的邮箱：**一个原生会话 = 一个邮箱账号**。会话之间用它互相发消息、派活、回结论。

两层结构：

| 层 | 给谁用 | 入口 |
|---|---|---|
| **MCP 层** | AI 会话（接入即用） | `mcp__mailbox__*` 那套工具 / `whoami`、`start_conversation`、`send_message`、`reply_message`、`mailbox_inbox`、`read_conversation`、`set_message_status` |
| **可视化层（前端）** | 人看 | `cli dashboard`（只读网页：在线情况、对话、投递积压、诊断） |

底层是一个 SQLite 库 + 一个 Broker（投递、重试、死信、维护循环）。默认库位置：`$MAILBOX_HOME/mailbox.sqlite3`，`MAILBOX_HOME` 缺省是 `~/.board-mcp`（Windows：`C:\Users\<你>\.board-mcp`）。

## 二、规则（产品语义，代码按这个执行）

### 1. 身份：会话 ID 就是账号身份

- 账号唯一键 = `(host_type, host_instance_id, native_session_id)`。
- **接入即注册**：MCP 服务器启动时按环境里的会话 ID 自动注册/复用账号，不需要人工点注册。
- 同一个会话 ID 重连 = **同一个账号**（只推进"连接代次"），不会产生第二个账号。
- 模型**不能**在工具里自报身份：所有发送类工具都没有 `from` / `agent` / `sender` 参数，发送者恒等于当前连接绑定的账号。

### 2. 账号名与密码（用户要求；**当前状态：设计已定，代码未实现**）

- **账号名（用户名）= 显示名**，全局唯一，可改；改名后旧名立刻释放。
- **密码 = 会话 ID**：接入时校验"名称 ↔ 会话 ID"必须配对；名字已被**别的会话**占用 -> **拒绝接入**。
- 实现方式：不需要额外的密码字段/哈希（会话 ID 本来就是账号身份的一部分），只要在注册事务里做唯一性检查 + 加一个唯一索引。
- ⚠️ **未实现**：这条约束的迁移（`v5`）和注册时的检查还没落地（上一轮被文件策略打断）。现在**允许重名**，也不校验配对。

### 3. 在线状态：严格参照进程

| 情形 | presence | 含义 |
|---|---|---|
| 托管该会话的进程活着 | `connected` | 在线：可以被直接投递、可以被叫醒开工 |
| 进程已退出 | `offline` | 离线：消息只排队，等它上线 |
| 连接没有进程信息 | `offline` | 同上（**不猜**，宁可判离线也不谎报在线） |

- **租约、心跳、`durable`、能力等级都不参与在线判定**（租约字段保留只为诊断）。
- 维护循环按进程存活回收连接（`mark_disconnected()`）：**进程还活着的连接永不因时间回收**。
- ⚠️ **已知缺口**：宿主身份只绑了一个整数 PID。PID 被复用、或有人直接改库把 `host_pid` 指向另一个活进程，都会显示"在线"。修法（未做）：记录并比对进程创建时间（`domain/process.py` 里已备好 `process_started_at()`），需要加一列 + 一次迁移。

### 4. 离线只存不发

- 目标离线时消息**持久化**在邮箱里，投递状态是 `queued`；**不尝试唤醒、不打开程序**，也不消耗重试次数。
- 目标上线后用 `mailbox_inbox` / `read_conversation` 取信即可。

### 5. 在线"直接接收并开工"（注入）

目标在线时，邮箱把消息**注入目标会话并让它开始一个回合**；两条通道按顺序试：

```
1) 通道B  plugin_channel  DSH 进程内插件（不需要任何凭据，装上就可用）
2) 通道A  http_channel    DSH 自己的本地接口 /api/session/prompt（需要签名密钥）
3) 报错                  两条都不行 -> 消息保持 queued，并写清各自为什么不行
```

- **只有宿主确认接收，投递才变 `delivered`**；没有通道时保持 `queued`（既不谎报 `delivered`，也不记成 `failed`）。
- 通道"能用但这次注入失败"（例如目标会话被别的写者占用）才记 `failed`（可重试，重试用尽进死信）。
- 通道不可用 vs 真失败的判别、以及"现在到底有哪条通道"，都能在 `whoami` / `doctor` 里看到（`wake_basis`、`wake_channel`、`wake_channels`）。

### 6. 投递状态字典

| 状态 | 含义 |
|---|---|
| `queued` | 已持久化在邮箱里。目标离线、或在线但没法注入，都停在这里 |
| `dispatched` | 已交给目标连接/通道，等宿主确认 |
| `delivered` | 宿主确认已接收（**不代表任务完成**） |
| `failed` | 真尝试过并失败，按退避重试 |
| `dead_letter` | 超过最大尝试次数或不可重试，等人工处理 |

`processing`（`pending/running/completed/blocked/cancelled/failed`）是**任务**状态，与投递状态相互独立。

## 三、安装与配置

### 1. 依赖

- Python ≥ 3.12（本仓库 `.venv`）+ `mcp` 包；测试用 `pytest`。
- 可选：Node.js（只用于跑 DSH 插件的纯逻辑测试）。

### 2. 建库

```powershell
cd E:\zcz\modle\MCP\mcp-agent-mailbox
.\.venv\Scripts\python.exe -X utf8 -m mcp_agent_mailbox.cli migrate --data-dir C:\Users\<你>\.board-mcp
```

### 3. 把邮箱接进 DSH（MCP 配置）

在 DSH 的 profile 里给邮箱服务器加一项（**会话身份必须由宿主编，不要让模型填**）：

```jsonc
{
  "transport": "stdio",
  "serverName": "mailbox",
  "command": "E:\\zcz\\modle\\MCP\\mcp-agent-mailbox\\.venv\\Scripts\\python.exe",
  "args": ["-m", "mcp_agent_mailbox.cli", "serve"],
  "env": {
    "MAILBOX_HOME": "C:\\Users\\<你>\\.board-mcp",
    "MAILBOX_SESSION_ID": "session-你的会话ID",
    "MAILBOX_DISPLAY_NAME": "DSH-A",
    "MAILBOX_HOST_TYPE": "dsh",
    "MAILBOX_HOST_INSTANCE_ID": "default",
    "MAILBOX_CAPABILITY_LEVEL": "0"
  },
  "cwd": "E:\\zcz\\modle\\MCP\\mcp-agent-mailbox"
}
```

- `MAILBOX_DISPLAY_NAME` 是账号名（用户名）；不填会退化成 `dsh/session-xxxx`。
- `MAILBOX_SESSION_ID` **必须是这条会话真实的 ID**，写错就会像"设置错了"那样：注册出来的账号绑在另一条会话上。
- `MAILBOX_CAPABILITY_LEVEL` 必须诚实：DSH 目前填 `0`。

### 4. 开启"直接开工"的注入通道

**通道 A（兜底，需凭据）**：在配置里加

```jsonc
"MAILBOX_DSH_WEB_URL": "http://127.0.0.1:19387",
"MAILBOX_DSH_HOME": "C:\\Users\\<你>\\.dsh"
```

密钥来自 `$DSH_HOME/.credentials.yaml` 里 `client-connection/browser-session` 记录的 `payload.secret`；读不到就自动判定该通道不可用（不会硬失败）。

**通道 B（优先，不需要凭据）**：安装本仓库的插件 `dsh-wake-plugin/`。

- 它暴露一个**只监听 127.0.0.1** 的入口：`POST /dsh-wake`（注入）、`GET /healthz`（探测），两者都要请求头 `x-dsh-wake-token`。
- 请求体：`{"sessionId": "<原生会话ID>", "text": "<要注入的用户消息>"}`；成功返回 `{"accepted": true}`。
- 插件做的事只有一件：`ctx.sessionController.resolveAgent(sessionId)` → `agent.followup(createUserMessage(...))`。**不改权限、不放宽审批、不碰会话日志文件。**
- 令牌没有或短于 16 字符时插件**拒绝启动**（宁可不注入，也不开一个谁都能往任意会话塞消息的口子）。
- 装载（官方机制二选一）：
  1. 用 DSH 的 `plugin_manager` `install_bundle`，`target` = `E:\zcz\modle\MCP\mcp-agent-mailbox\dsh-wake-plugin` 的绝对路径；
  2. 或在 `$DSH_HOME/cordis.patch.yml` 里加一行 `cordis:include`，指向该目录的 `dsh-wake-include.patch.yml`（需要一次工作区外写入批准）。
- 邮箱侧要与之配对：`MAILBOX_DSH_WAKE_TOKEN`（同一个令牌）、可选 `MAILBOX_DSH_WAKE_URL`（默认 `http://127.0.0.1:8799/dsh-wake`）。

> 实测记录：**通道 A 已端到端打通**（见"五、验证"）；**通道 B 尚未安装**（8799 无监听），插件逻辑本身用 Node 测过 9/9 通过。

## 四、怎么用

### 1. AI 侧（MCP 工具）

| 工具 | 用途 |
|---|---|
| `whoami()` | 我是谁、在线吗、能不能被注入（`wake_basis` / `wake_channel` / `wake_channels`）、还有几条未读 |
| `list_contacts(status?, host_type?, limit?)` | 有哪些账号、在线与否、能否被直接注入（`reachable_now` / `can_wake`） |
| `start_conversation(to_account_id, text, idempotency_key?, wait_for_reply?)` | 主动发起对话并发出第一条 |
| `send_message(conversation_id, text, ...)` | 继续发 |
| `reply_message(message_id, text, ...)` | 回复某条（收件人固定为原发送者） |
| `mailbox_inbox(limit?)` | **收件侧开工入口**：取未读、给出 `reply_with` / `mark_done_with` 现成参数（只读） |
| `list_conversations(unread_only?, cursor?, limit?)` | 我的对话列表 |
| `read_conversation(conversation_id, mark_seen?)` | 读全文（`mark_seen=False` 为只读） |
| `set_message_status(message_id, processing, result?)` | 回执（`completed` **不等于**回复，结论要用 `reply_message`） |
| `mailbox_register` / `connect_mailbox` | 显式注册（默认关闭，需 `--allow-adapter-registration`） |
| `mailbox_heartbeat` / `mailbox_fetch_delivery` / `mailbox_ack_delivery` / `mailbox_fail_delivery` | 宿主适配器协议（心跳、按投递取全文、确认、报失败） |

典型流程：

```
收到注入/取信  -> mailbox_inbox 拿到正文与参数
干活          -> reply_message 把结论发回去
             -> set_message_status(completed) 留回执
```

### 2. 人侧（命令行）

```powershell
$py = "E:\zcz\modle\MCP\mcp-agent-mailbox\.venv\Scripts\python.exe"
& $py -X utf8 -m mcp_agent_mailbox.cli migrate      --data-dir C:\Users\<你>\.board-mcp
& $py -X utf8 -m mcp_agent_mailbox.cli accounts     --data-dir C:\Users\<你>\.board-mcp
& $py -X utf8 -m mcp_agent_mailbox.cli inbox <account_id>       # 只读：某账号待办
& $py -X utf8 -m mcp_agent_mailbox.cli conversations <account_id>
& $py -X utf8 -m mcp_agent_mailbox.cli deliveries <account_id>  # 看 queued/failed/死信
& $py -X utf8 -m mcp_agent_mailbox.cli doctor                   # 数据库、在线分布、通道现状
& $py -X utf8 -m mcp_agent_mailbox.cli adapters                 # 宿主能力矩阵
& $py -X utf8 -m mcp_agent_mailbox.cli dashboard --data-dir C:\Users\<你>\.board-mcp --port 8765
```

`dashboard` 会打印一条**带一次性令牌**的网址，浏览器打开即可（只读，页面没有任何写入口）。

### 3. 前端（可视化层）

五个区域：**总览 / 账号 / 对话与消息 / 投递 / 诊断**。账号页显示：

- `在线 · 托管进程活着` / `离线 · 消息排队等它上线`（只有两态）；
- 托管进程 PID（没有进程信息就写"无进程信息"）；
- 注入能力徽章：`可直接注入开工` / `声明可注入（未验证）` / `无注入通道 · 等对方取信` / `离线 · 只存不发`。

### 3. 端到端（实测步骤与结论）

```powershell
# 先看通道现状（B 装了没有、A 的凭据能不能读）
.\.venv\Scripts\python.exe -B -X utf8 -c "import sys;sys.path.insert(0,'.');from mcp_agent_mailbox.adapters.dsh_wake_chain import DshWakeChain;print(DshWakeChain.from_environment().channel_status())"

# 直接对某条会话注入一条
.\.venv\Scripts\python.exe -B -X utf8 -c "import sys;sys.path.insert(0,'.');from mcp_agent_mailbox.adapters.dsh_wake_chain import DshWakeChain;print(DshWakeChain.from_environment().wake('session-目标ID','测试文本'))"
```

**已实测通过的结论：**

1. 通道 A 的报文格式**必须**是三层包裹（实测被 DSH 逐层拒绝过两次才对）：

   ```jsonc
   POST http://127.0.0.1:19387/api/session/prompt
   Cookie: dsh-auth-<base64url(sha256(authority))>=v1.<body>.<sig>
   {
     "type": "client-request",
     "rpcId": "<uuid>",
     "method": "session/prompt",
     "payload": { "args": { "request": {
        "requestId": "<uuid>", "sessionId": "<目标会话ID>",
        "mode": "queue", "content": [{ "type": "text", "text": "<文本>" }]
     } } }
   }
   ```

   错误对照：`payload` 少 `args` → `gateway/internal: Remote payload must contain exactly one plain-object args field`；`args` 少 `request` → `gateway/arguments-invalid: ... missing "request"`。用错格式时**不能**算"通道不可用"（那是真失败，会重试）。

2. **写入邮箱 → 自动投递 → `delivered`** 全链路实测通过：以另一账号写入消息后，`dispatch_due()` 输出 `dispatched=1`，投递最终状态 `delivered`、`last_error=None`。

3. **注入确实会拉起一个回合**：被注入的会话里出现了一条消息并触发了新一轮（可以在会话日志里看到它是以 `agent/inbox/spliced(target=next-turn)` 进入、紧跟 `turn/start`；它与"人从客户端手打的消息"可以用 source 字段区分）。

## 六、当前状态与限制（如实）

**已验证**
- 在线严格参照进程：杀掉托管进程 0.3–0.5 秒内变 `offline`；把租约改成 1999 年仍显示 `connected`；没有进程信息的连接立即判离线并被回收。
- 离线只存不发：投递保持 `queued`、`attempt` 不增长、审计里没有任何 `wake.*` 尝试。
- 回补投：离线期间的消息，在同一会话 ID 的进程重新上线后能取到。
- 通道 A 注入链路：见上。
- 通道 B 插件逻辑：Node 测试 9/9。

**未实现 / 未完成**
1. **账号名唯一 + 密码（会话 ID）配对校验**：设计已定，代码未写（迁移 `v5`、注册时的检查、4 个用例都还没落地）。现在允许重名。
2. **通道 B 还没装进 DSH**：`dsh-wake-plugin/` 已写好、逻辑测过，但没有 `install_bundle`，8799 端口无监听，所以现在实际生效的是兜底的通道 A。
3. **宿主身份只绑 PID**：PID 复用/改库可冒充在线（见 §二.3 的缺口说明）。
4. **前端只读**：页面上不能改账号名（"账号信息后续可修改"目前只能靠重连时传新名字实现）。
5. **每个会话要一份 MCP 配置项**：静态 `env` 无法区分多个会话，多会话需要多份配置。
6. **注入文本只写"去取信"提示**，不把消息正文塞进 DSH 会话日志；正文始终由邮箱按权限给出。

**环境注意（不影响产品逻辑）**
- 若 `$DSH_HOME/.credentials.yaml` 不存在，通道 A 自动判定不可用（DSH 侧没激活该插件或 home 不对时就是这样）。
- 受限沙箱下，本会话派出的进程可能无法创建目录，会导致 pytest 建不了临时目录；`run_tests.py` 已能自动挑可写临时根并每次用唯一 `basetemp`。

## 七、排错

| 现象 | 原因 | 处理 |
|---|---|---|
| `whoami` 显示 `bound=false` | 适配器没注入 `MAILBOX_SESSION_ID` | 在客户端配置里注入会话身份后重启该 MCP 服务器 |
| 账号名不是你要的（如 `dsh/session-xxxx`） | 没配 `MAILBOX_DISPLAY_NAME` | 配上它再重启 |
| 账号绑到了别的会话上 | `MAILBOX_SESSION_ID` 写错 | 改成该会话真实的 ID（宿主的会话 ID 可以用 `echo $env:DSH_SESSION_ID` 核） |
| `can_wake=false` | 两条通道都不可用 | 看 `whoami.wake_channels` 的 `detail`：B 缺令牌/没装插件，A 读不到密钥 |
| 消息一直 `queued` | 目标离线，或在线但没通道 | 等目标上线；或按 §三.4 开通通道 |
| 投递反复 `failed` 最后死信 | 通道能用但一直失败 | 看 `deliveries.last_error`；修好后用新消息重试 |
| 日志里看不到正文 | 默认脱敏（刻意） | 需要时显式开 `MAILBOX_LOG_MESSAGE_CONTENT`（有泄露风险） |
| 前端打不开 | 没建库 / 端口被占 | 先 `migrate`；换 `--port` |
